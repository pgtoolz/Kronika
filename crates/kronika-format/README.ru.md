# kronika-format

[English version](README.md)

`kronika-format` задаёт двоичный контракт для записи и чтения сегментов
Kronika. Это не самостоятельный конвертер и не универсальный формат
аналитических данных.

Данные проходят через следующие компоненты:

```text
Linux / cgroup / PostgreSQL / PostgreSQL log
        |
        v
kronika-collector collects one window
        |
        v
kronika-registry encodes typed rows as section bodies
        |
        v
kronika-writer builds a ZMS part
        |
        v
$KRONIKA_STORAGE_DIR/active.wal
        |
        | write_segment()
        v
$KRONIKA_STORAGE_DIR/YYYY/MM/DD/N.zms
        |
        v
kronika-store / kronika-reader
        |
        v
kronika-web
```

Журнал всегда находится в `$KRONIKA_STORAGE_DIR/active.wal`. Готовые файлы ZMS
записываются в строгое календарное дерево UTC:

```text
$KRONIKA_STORAGE_DIR/
|-- active.wal
`-- YYYY/
    `-- MM/
        `-- DD/
            `-- N.zms
```

`N` — десятичный [`SegmentId`](../kronika-layout/src/time.rs): метка Unix в
микросекундах для первого окна сбора, успешно добавленного в сегмент.
`YYYY/MM/DD` — день UTC, вычисленный из этого идентификатора.

Строковые значения не хранятся в отдельных файлах. Пока сегмент открыт,
словарные тела находятся в ZMS-частях внутри `active.wal`. При завершении
записи код декодирует и нормализует их: готовый `.zms` содержит не более одного
тела `dict.strings` и одного тела `dict.blobs`.

Крейт задаёт байтовую структуру `ZMS1` и `ZMSP`, концевой каталог, контрольные
суммы CRC32C, `StrId` и модель словаря с заданными пределами. Другие крейты
отвечают за:

- семантику Linux и PostgreSQL и схемы секций —
  [`kronika-registry`](../kronika-registry/src/lib.rs);
- кодирование Parquet, буферизацию, ввод-вывод журнала и запись сегментов —
  [`kronika-writer`](../kronika-writer/README.md);
- интервалы сбора, ротацию и ограничения источников —
  [`kronika-collector`](../../bins/kronika-collector/README.md);
- пути каталога данных, строгий обход и права записи —
  [`kronika-layout`](../kronika-layout/);
- типизированные запросы, HTTP, сроки хранения, шифрование и удалённое
  хранилище.

## От окон сбора к сегменту

Сборщик держит один словарь строк (интернер) на весь открытый сегмент и создаёт новые
буферы записей для каждого непустого цикла сбора. Реестр сортирует каждую секцию
снимка по ключу контракта и кодирует её. Код записи добавляет словарные записи
текущего окна, строит ZMS-часть, помещает её в кадр `ZMSP`, дописывает в
`active.wal` и вызывает `sync_data`. После успешного добавления интернер
оставляет для уже записанных значений только компактные данные для проверки
идентификаторов, поэтому следующие окна не записывают эти значения повторно.

Сборщик добавляет окна, пока сегмент не потребуется закрыть по размеру,
возрасту, принудительной ротации или пределу журнала. Затем `write_segment`:

1. Проверяет каталог каждой записанной части и каждый читаемый диапазон тела.
2. Группирует зарегистрированные секции данных по `type_id`, декодирует тела
   Parquet и объединяет строки.
3. Сортирует каждую объединённую секцию по ключу реестра, а затем по всем
   остальным столбцам, задавая детерминированный полный порядок.
4. Нормализует словарные записи по `str_id`: удаляет точные повторы и отклоняет
   конфликты значений, метаданных или размещения.
5. Заново кодирует каждый непустой тип в одно каноническое тело Parquet и
   записывает плотно упакованный ZMS с одним концевым каталогом.
6. Синхронизирует соседний временный файл, созданный текущим вызовом, и
   публикует его жёсткой ссылкой без замены существующего файла.

Сборщик сбрасывает `active.wal` только после успешной публикации.
`write_segment` убирает структуру Parquet для отдельных окон и повторные записи
каталога. Тела из журнала декодируются и кодируются заново, а не копируются в
готовый ZMS.

### Окна, части, секции и тела

В формате используются четыре уровня:

- **окно сбора** — один непустой цикл сборщика;
- **ZMS-часть** — запись одного окна в собственном кадре со своими `ZMS1`,
  телами, каталогом и хвостовым индексом;
- **секция** — одна запись каталога: `type_id`, смещение, длина, число строк и
  CRC32C;
- **тело секции** — диапазон байтов, на который указывает запись каталога;
  код записи помещает в этот диапазон один самодостаточный файл
  Parquet.

Пока сегмент открыт, каждая часть находится в отдельном кадре журнала:

```text
active.wal
|
+-- ZMSP frame #1
|   `-- ZMS part for window #1
|       |-- "ZMS1"
|       |-- data section bodies
|       |-- new dict.strings / dict.blobs records
|       |-- part catalog
|       `-- tail index
|
`-- ZMSP frame #2
    `-- ZMS part for window #2
        |-- "ZMS1"
        |-- data section bodies
        |-- new dict.strings / dict.blobs records
        |-- part catalog
        `-- tail index
```

В каждой части непустые тела данных расположены по возрастанию `type_id`, за
ними идут `dict.strings` и `dict.blobs`. Отсутствующая словарная секция не
занимает места. В готовом ZMS действует тот же канонический порядок: каждый
непустой тип встречается один раз, типы данных идут по возрастанию, а два
необязательных словаря завершают список. Код чтения находит каждое тело через
каталог.

При завершении сегмента кадры отдельных частей исчезают:

```text
active.wal                         YYYY/MM/DD/N.zms

ZMSP [part for window #1]             "ZMS1"
ZMSP [part for window #2] -- write_segment() -> one canonical body per populated data type
...                                  optional normalized dict.strings
                                     optional normalized dict.blobs
                                     one shared end catalog
                                     one tail index
```

В готовом ZMS нет явных маркеров границ окон. Строки всех окон одного типа
находятся в одном каноническом теле, а исходная часть строки не записывается.
Каталог описывает физические секции, а не номера окон.

## Структура готового сегмента v1

Все целые числа записаны в формате little-endian. Канонический вывод размещает
поля плотно, без отступов для выравнивания. Пусть каталог содержит `N`
записей, а все тела секций занимают `B` байт:

```text
offset  size          contents
0       4             "ZMS1"
4       B             section body 0, section body 1, ... in catalog order
4+B     32*N          catalog entries
...     32            catalog metadata
...     8             tail index
```

Точный размер файла:

```text
zms_bytes = B + 32*N + 44
catalog_len = 32*N + 32
```

Постоянные 44 байта приходятся на начальную сигнатуру, метаданные каталога и
хвостовой индекс. Внешнего слоя сжатия нет. Эти формулы описывают канонический
вывод. `validate_catalog_layout`, проверка частей и код физического чтения
требуют, чтобы диапазоны тел непрерывно шли от начальной сигнатуры до каталога.
Они отклоняют несмежные диапазоны, пересечения, лишние байты после тел,
повторные типы, ненулевые флаги, пустые объявленные секции и неканонический
порядок.

### Запись каталога: 32 байта

| Смещение | Поле | Тип | Значение |
| ---: | --- | --- | --- |
| 0 | `type_id` | `u32` | Схема секции, зарегистрированная в `kronika-registry`. |
| 4 | `flags` | `u32` | Зарезервировано; код записи сохраняет ноль. |
| 8 | `offset` | `u64` | Абсолютное смещение тела от первого байта файла. |
| 16 | `len` | `u64` | Длина тела в байтах. |
| 24 | `rows` | `u32` | Число логических строк в теле. |
| 28 | `crc32c` | `u32` | CRC32C тела секции. |

Каждый непустой `type_id` встречается ровно один раз. Секции данных идут по
возрастанию `type_id`, затем расположены не более одного `dict.strings` и не
более одного `dict.blobs`. Строки из разных окон и сущности разных графиков
объединяются в одном теле своего типа.

### Метаданные каталога: 32 байта

| Смещение | Поле | Тип | Значение |
| ---: | --- | --- | --- |
| 0 | `min_ts` | `i64` | Самая ранняя метка времени секции, микросекунды Unix. |
| 8 | `max_ts` | `i64` | Самая поздняя метка времени секции, микросекунды Unix. |
| 16 | `entry_count` | `u32` | Число 32-байтных записей перед этим блоком. |
| 20 | `format_version` | `u32` | Версия структуры контейнера; код записи сохраняет `1`. |
| 24 | `crc32c` | `u32` | CRC32C записей и метаданных; при расчёте это поле обнуляется. |
| 28 | `window_count` | `u32` | Число окон сбора, объединённых в контейнере. `build_part` сохраняет `1`, `write_segment` — точное число частей журнала; ноль означает «неизвестно». |

### Хвостовой индекс: 8 байт

| Смещение | Поле | Тип | Значение |
| ---: | --- | --- | --- |
| 0 | `catalog_len` | `u32` | Записи и 32-байтный блок метаданных без самого хвостового индекса. |
| 4 | `magic` | 4 байта | `"ZMS1"`. |

Чтение начинается с конца файла:

1. Прочитать последние восемь байт.
2. По `catalog_len` найти начало каталога.
3. Декодировать каталог и проверить его CRC32C.
4. Прочитать нужное тело по абсолютным `offset` и `len`.
5. Проверить CRC тела и только затем передать байты кодеку реестра.

### Пример снимка и двух словарей в одном ZMS

Упрощённый ZMS для узла Linux содержит тело `os_process`, словарное тело для
коротких строк и словарное тело для больших значений. Обозначим их размеры как
`S`, `T` и `L`, где `B = S + T + L`.

```text
offset

0       +----------------------------------------------------------+
        | "ZMS1"                                                   | 4 bytes
4       +----------------------------------------------------------+
        | body #0: os_process, type_id=1_100_001             | S bytes
        | Parquet: ts | pid | comm=H | cmdline=Q | ...             |
4+S     +----------------------------------------------------------+
        | body #1: dict.strings, type_id=3_001_001                 | T bytes
        | Parquet: str_id | bytes                                  |
4+S+T   +----------------------------------------------------------+
        | body #2: dict.blobs, type_id=3_002_001                   | L bytes
        | Parquet: str_id | stored_bytes | full_len | ...          |
4+B     +----------------------------------------------------------+
        | catalog entry #0: type=1_100_001, offset=4, len=S        | 32 bytes
36+B    | catalog entry #1: type=3_001_001, offset=4+S, len=T      | 32 bytes
68+B    | catalog entry #2: type=3_002_001, offset=4+S+T, len=L    | 32 bytes
100+B   +----------------------------------------------------------+
        | catalog metadata                                         | 32 bytes
132+B   +----------------------------------------------------------+
        | catalog_len=128 | "ZMS1"                                 | 8 bytes
140+B   +----------------------------------------------------------+
```

Для трёх тел `catalog_len = 3 * 32 + 32 = 128`, поэтому весь файл занимает
`B + 140` байт. Если в окне нет больших значений, тело `dict.blobs` и его
запись каталога отсутствуют. Каждое непустое окно может добавить строки, но в
готовом каталоге каждый непустой `type_id` всё равно встречается один раз.

Kronika кодирует каждое тело данных или словаря как самодостаточный файл
Parquet с собственными маркерами `PAR1 ... PAR1`. Контейнер ZMS считает эти
байты непрозрачными и не разбирает метаданные столбцов. Показанные выше строки
Parquet — декодированное содержимое, а не буквальный текст в файле. Из-за
внутреннего кодирования и Zstd исходные текстовые байты могут отсутствовать в
ZMS как непрерывная последовательность.

Побайтовая фикстура [`minimal.zms`](tests/fixtures/minimal.zms) занимает
80 байт: `ZMS1`, четырёхбайтное тело `01 02 03 04`, одна запись каталога,
метаданные и хвостовой индекс. В [`tests/fixture.rs`](tests/fixture.rs)
зафиксировано каждое смещение, а кодировщик проверяется на точное
воспроизведение фикстуры.

## Кодирование тел секций

`kronika-format` допускает непрозрачные тела, но Kronika хранит секции снимков
и словарей как самодостаточные файлы Parquet. Для частей журнала и готовых
сегментов используются разные профили записи:

- тело окна сбора использует Zstd уровня 3; строки снимка сортируются по ключу
  реестра, а строки словаря — по `str_id`;
- итоговое тело использует Parquet 1.0, значения PLAIN, уровни RLE и Zstd
  уровня 6; Parquet может разбить его на несколько страниц или групп строк,
  а словарное кодирование, статистика и индексы смещений отключены;
- канонический порядок строк данных задают ключ реестра и все остальные
  столбцы; нормализованные строки словаря сортируются по `str_id`;
- число строк секции ограничено полем `u32` каталога; закодированное тело и
  суммарная работа декодирования ограничены пределом версии 1 в 1 GiB;
- лишние метаданные схемы Arrow не записываются, а `created_by` остаётся
  пустым.

Каждое окно сбора проверяется отдельно и добавляется без прогноза размера
будущей объединённой секции. Сегмент закрывается по настроенному размеру
журнала после успешного добавления либо по возрасту. Финализатор проверяет
ширину полей каталога, суммарную работу декодирования, арифметику и фактический
размер тела по пределам версии 1. Консервативная граница учитывает все страницы:

```text
body_bound = 64 KiB + sum(zstd_bound(page_inputs_i) + page_count_i * 4 KiB)
body_bound <= 1 GiB
```

Для зафиксированного контракта Zstandard:

```text
zstd_bound(n) = n + floor(n / 256)
              + (n < 128 KiB ? floor((128 KiB - n) / 2048) : 0)
```

Слагаемое 4 KiB ограничивает заголовок страницы и метаданные блока столбца, а
64 KiB — структуру файла Parquet. При декодировании каждой части
`write_segment` заново вычисляет многостраничную границу и проверяет
фактический размер закодированного тела по пределу 1 GiB.

Без вложенной схемы Arrow каждое тело не содержит дубликат логической схемы;
точная экономия зависит от контракта секции. Физическая схема Parquet остаётся,
потому что она нужна декодеру для расположения столбцов.

Весь файл не сжимается одним потоком Zstd. Заголовок и конец каждого тела
Parquet, каталог ZMS и структура ZMS/ZMSP находятся вне общего потока. Код
чтения может найти и проверить одно тело, не распаковывая остальные секции.

## Хранение строковых значений

Секция снимка не хранит исходный текст в каждой записи. Столбец `StrId`
содержит только `u64`, равный `xxh3_64(original_bytes)`. Ноль означает «нет
значения». Это число — не файловое смещение: исходные байты нужно найти под тем
же идентификатором в отдельных словарных телах Parquet.

`kronika-writer` создаёт два типа словарных секций:

| `type_id` | Секция | Столбцы после декодирования |
| ---: | --- | --- |
| `3_001_001` | `dict.strings` | `str_id`, полное значение `bytes` |
| `3_002_001` | `dict.blobs` | `str_id`, `stored_bytes`, `full_len`, `truncated`, необязательный `full_sha256` |

Обе секции находятся **внутри ZMS**, рядом с секциями снимков. `dict.blobs` —
не отдельный файл, не PostgreSQL TOAST и не внешнее объектное хранилище.

### Короткая строка `postgres`

Для байтов `postgres`
`H = xxh3_64(b"postgres") = 0x0939566173e67ada`. Если два процесса в одном
окне имеют это имя, данные размещаются в одном физическом файле. Ниже показано
содержимое Parquet после декодирования; остальные тела опущены:

```text
$KRONIKA_STORAGE_DIR/YYYY/MM/DD/N.zms  (one file)

[ "ZMS1" ]
[ os_process Parquet body, type_id=1_100_001
  after decoding:
  pid | comm
  101 | H
  102 | H ]
[ dict.strings Parquet body, type_id=3_001_001
  after decoding:
  str_id | bytes
  H      | b"postgres" ]
[ end catalog
  offset,len -> entire os_process body
  offset,len -> entire dict.strings body ]
[ tail index ]
```

Секция снимка содержит два логических значения `StrId`, представленных как
`u64`, а словарь — одну запись с байтами `postgres`.

Справочная секция `os_user` использует то же представление: она хранит одно
интернированное имя для наблюдаемого UID, а строки процессов сохраняют числовые
реальный и эффективный UID. Поэтому повторяющиеся процессы не дублируют имя.
Справочную строку и её запись `dict.strings` сохраняет обычный код записи
журнала и формирования ZMS. Восстановление после перезапуска и нормализация
словаря остаются прежними.

Каталог указывает на словарное тело:

```text
ZMS catalog entry: type_id=3_001_001, offset=X, len=T
                            |
                            v
byte range [X, X+T): self-contained Parquet body
|-- "PAR1"
|-- row group #0
|   |-- str_id column chunk: encodes H
|   `-- bytes column chunk: encodes b"postgres"
|-- Parquet metadata and metadata length
`-- "PAR1"
```

Байты находятся в блоке столбца `bytes` тела `dict.strings`. В готовом ZMS
Parquet помещает значение PLAIN на страницу данных столбца, которую сжимает
Zstd уровня 6. Тело `os_process` хранит только `H`. Каталог ZMS содержит
смещение и длину всего словарного тела, а не отдельного значения; более точные
смещения находятся в метаданных Parquet. Чтобы найти значение по `H`, нужно
декодировать словарное тело. Соответствующее тело в части журнала использует
профиль окна сбора с Zstd уровня 3.

Блоки `after decoding` показывают логические значения, а не байты на диске.
Две ссылки необязательно занимают ровно 16 байт, а из-за кодирования и сжатия
`postgres` может отсутствовать в файле как непрерывная последовательность
байтов.

Чтение идёт через концевой каталог:

```text
(1) tail index -> end catalog

(2) catalog -> os_process body
            -> decode Parquet
            -> comm=H

(3) catalog + H -> every dict.strings and dict.blobs body
                -> decode record with str_id=H
                -> b"postgres"
                -> comm="postgres"
```

В ZMS нет глобального индекса `StrId -> offset`. Полное чтение словаря
посещает каждое тело `dict.strings` и `dict.blobs` и строит отображение в
памяти. При индексировании выбранных значений код также читает словарные тела,
но сохраняет только заранее заданные идентификаторы.

### Большие и усечённые значения

Сборщик использует `DictLimits::default()`. Значения размещаются так:

| Исходное значение | Секция | Байты, сохранённые на диске |
| --- | --- | --- |
| `postgres`, 8 байт | `dict.strings` | Все 8 байт. |
| Текст плана, 20 KiB | `dict.blobs` | Все 20 KiB, `full_len=20,480`, `truncated=false`, без SHA-256. |
| `/proc/PID/cmdline`, 80 KiB | `dict.blobs` | Все 80 KiB, `full_len=81,920`, `truncated=false`, без SHA-256. |
| Значение размером 2 MiB | `dict.blobs` | Первый 1 MiB, `full_len=2,097,152`, `truncated=true` и SHA-256 исходных 2 MiB. |

`StrId` усечённого значения вычисляется по всем исходным байтам, а не по
сохранённому префиксу. Отброшенный суффикс нельзя восстановить из ZMS. Если
источник ограничивает длину значения, он делает это до интернирования, поэтому
словарь считает полученные байты полным значением.

Стандартные пределы:

| Ограничение | Значение | Действие |
| --- | ---: | --- |
| Порог `dict.blobs` | 4 KiB | Значения не короче порога попадают в `dict.blobs`. |
| Предел усечения | 1 MiB | У более длинного значения сохраняется префикс ровно этой длины. |
| Предел сохранённых байтов | 64 MiB | Обычное новое значение отклоняется при превышении предела; обязательные значения `dict.hot_strings` добавляются и при его превышении. |

Эти значения заданы в коде, а не в переменных окружения. Предел учитывает
байты значений после усечения, но не метаданные Parquet. Для обычного нового
значения превышение возвращает `DictError::Full`. Байты обязательных значений
`dict.hot_strings` входят в общий счётчик, но превышение предела не запрещает
их добавление. Поэтому размер закодированной секции может превысить этот предел.

`SegmentDicts` также моделирует подмножество `dict.hot_strings`, но
`kronika-writer` не создаёт третью словарную секцию. Эти значения попадают в
обычное тело `dict.strings`; тела `dict.hot_strings` в файле нет.

### Дедупликация словаря

Один `Interner` действует на протяжении всего открытого сегмента. Его текущий
`SegmentDicts` обнаруживает коллизии хэша и хранит одну копию одинаковых
байтов. После записи окна в журнал `flush_window` заменяет байты компактными
метаданными значения. Следующие окна не записывают то же значение повторно,
если не требуется более строгое размещение.

`write_segment` нормализует все словарные записи журнала. Разные байты или
метаданные значения в `dict.blobs` для одного `str_id`, а также конфликт
размещения между `dict.strings` и `dict.blobs` приводят к ошибке записи.
Результат сортируется по `str_id` и содержит не более одной физической записи
на идентификатор либо в `dict.strings`, либо в `dict.blobs`. Код физического
чтения отклоняет повторные типы словарных секций, а идентификаторы внутри
каждого тела должны строго возрастать.

## `active.wal` и восстановление после сбоя

`active.wal` — журнал незавершённого сегмента в корне каталога данных. Журнал
версии 1 начинается с 36-байтного заголовка с контрольной суммой:

```text
"KRNJNL1\0" | version: u32 | state: u8 | id_present: u8 | reserved: u16
             | segment_id: i64 | body_len: u64 | header_crc32c: u32
```

Заголовок хранит пустое состояние либо точный `SegmentId` активного сегмента и
число байтов следующих кадров. Каждый кадр содержит 16-байтный заголовок и одну
полную ZMS-часть:

```text
"ZMSP" | part_len: u64 | header_crc32c: u32 | ZMS part
```

Контрольная сумма заголовка журнала покрывает первые 32 байта, а контрольная
сумма заголовка кадра — первые 12 байт. ZMS-часть содержит свои `ZMS1`, тела,
каталог и хвостовой индекс, поэтому кадр можно проверить до принятия.
Канонический пустой журнал — 36-байтный пустой заголовок, а не файл нулевой
длины.

Для неповреждённого журнала обозначим через `P` число кадров, через `N_in` —
общее число записей каталогов частей, а через `B_in` — число байтов во всех
входных телах. Пусть `K` — число непустых типов после объединения, а `B_out` —
число байтов в их канонических перекодированных телах:

```text
active_parts_bytes     = 36 + B_in + 32*N_in + 60*P
finished_zms_bytes     = B_out + 32*K + 44
journal_minus_finished = (B_in - B_out) + 32*(N_in - K) + 60*P - 8
```

Итоговое тело занимает не более 1 GiB, поэтому для контейнера действует ещё
одно ограничение:

```text
B_out <= 1 GiB * K
finished_zms_bytes <= (1 GiB + 32) * K + 44
```

Среди `K` нет повторных `type_id`. Формулы размера учитывают перекодирование
Parquet, удаление тел и записей каталога для отдельных окон, нормализацию
словарей и удаление структуры кадров.

У версии 1 есть три абсолютных ограничения: одна ZMS-часть занимает не более
64 MiB, журнал содержит не более 1,000,000 кадров, а физический файл журнала
занимает не более 1 GiB с учётом временного маркера сброса. Настройки могут
только уменьшить эти пределы. Потоковый сканер держит в памяти одно тело
ZMS-части с заданным пределом и возвращаемые ссылки на кадры. Он останавливается
на первом повреждённом кадре и не ищет новую сигнатуру внутри повреждённых
байтов.

`Journal::open` версии 1 отклоняет журнал при любой ошибке проверки. Метод
проверяет весь заголовок, записанную длину тела и каждый кадр. Файл без
заголовка, другая версия, повреждённый из-за неполной записи заголовок,
несовпадение длины и любой неполный или повреждённый кадр приводят к ошибке;
файл остаётся без изменений. Файл нулевой длины инициализируется каноническим
пустым заголовком. Классификация повреждений в низкоуровневом сканере не
исправляет журнал.

При запуске сборщик завершает корректный активный журнал с сохранённым
`SegmentId` и публикует `YYYY/MM/DD/N.zms`. Сброс разрешён только после
успешной публикации. Сначала сохраняется маркер фиксации. Затем код записывает
`JournalHeader::EMPTY` и вызывает `sync_data`, пока маркер и тело кадров ещё
сохранены, усекает файл до 36 байт и снова вызывает `sync_data`. Если процесс
завершится после синхронизации маркера, следующий `Journal::open` проверит его
и закончит сброс.

Маркер сброса занимает 32 байта и хранит прежнюю длину журнала, `SegmentId` и
контрольную сумму заголовка. Настроенный предел относится к физическому размеру
файла: код записи резервирует эти 32 байта перед каждым добавлением, включая
первый кадр.

## Настройки размера файла

У структуры ZMS нет настроек сжатия. Интервалы источников задают частоту
снимков. Размер и возраст сегмента определяют, сколько данных входит в один
файл и сколько окон объединяет `write_segment`. Предел журнала вызывает
досрочную запись сегмента и не задаёт целевой размер ZMS. Сборщик не
ограничивает число строк по источнику.

Переменные и стандартные значения перечислены в
[настройках сборщика](../../bins/kronika-collector/README.md).

### Нереализованные подходы

| Подход | Источник экономии | Ограничение |
| --- | --- | --- |
| Более высокий уровень Zstd для финального Parquet | Страницы внутри одного тела могут стать меньше. | Требует больше CPU; финальные тела уже используют уровень 6, тела окон сбора — уровень 3. |
| Внешнее сжатие всего ZMS | Один поток видит повторяющиеся словари, концевые метаданные и похожие окна. | Теряется прямой доступ к телу по `offset`; это заменило бы семантику доступа ZMS. |

## Целостность и ограничения

CRC32C покрывает каждое тело секции, каталог и каждый заголовок `ZMSP`. Она
обнаруживает случайное повреждение, но не служит аутентификацией, подписью или
шифрованием.

`kronika-format` проверяет структуру кадров, длину и контрольную сумму каталога,
границы секций и контрольные суммы секций в полных частях. Код чтения готовых
сегментов принимает версию контейнера 1 и ограничивает размеры каталога,
секций, строк и групп строк. Несовместимая схема секции получает новый
`type_id`; при изменении структуры ZMS нужна новая версия контейнера.

- [`src/dictionary.rs`](src/dictionary.rs) описывает инварианты словаря;
- [`kronika-registry`](../kronika-registry/src/lib.rs) описывает схемы секций и
