# kronika-writer

[English version](README.md)

`kronika-writer` преобразует одно или несколько ограниченных окон сбора в
ZMS-сегмент и сохраняет его на диске. Крейт хранит буферы секций в памяти,
заменяет повторяющиеся строки ссылками на общий словарь сегмента, ведёт журнал `active.wal` версии 1,
восстанавливает его и публикует готовые сегменты. Запросы к источникам,
байтовое представление формата и грамматика каталога данных реализованы в
других крейтах.

## Окно сбора

`SectionBuffers::push<T: Section>` сохраняет строки по зарегистрированным типам.
Буфер типа заполняется до `SECTION_WRITE_BATCH_ROWS`, после чего метод возвращает
отклонённую строку: вызывающий код может вызвать `flush` и повторить попытку без
потери данных. `flush` кодирует секции данных в порядке `type_id`, добавляет
секции словаря, вычисляет временной диапазон каталога и возвращает одну
ZMS-часть. После успешного `flush` буферы записей пусты.

`dict::encode` преобразует текущее окно интернера в отсортированные секции
`dict.strings` и `dict.blobs`. Строки снимка ссылаются на эти значения по
`str_id`.

## Интернер

`Interner` — словарь одного открытого сегмента: он сопоставляет каждому
значению идентификатор, на который ссылаются строки данных. Текущее окно хранит полные байты в пределах
`DictLimits`. После успешной записи окна `flush_window` заменяет эти байты
компактными метаданными для обнаружения коллизий, дедупликации и итогового
размещения. Байты уже записанных значений не остаются в памяти до записи
сегмента.

Если возникает коллизия, конфликт размещения или превышение байтового предела,
состояние до вызова не меняется. `DictError::Full` сообщает вызывающему коду,
что пора записать сегмент или сбросить буфер окна.

## Журнал

`Journal::open(&WriterOwner, config)` открывает корневой `active.wal` через
`WriterOwner` из `kronika-layout`. Новый журнал инициализируется записанным на
диск 36-байтовым пустым заголовком версии 1; пустой журнал никогда не
представлен файлом нулевой длины.

Журнал версии 1 использует сигнатуру `KRNJNL1\0`. Заголовок с контрольной суммой
хранит состояние журнала — пустой он или активный, [`SegmentId`][layout]
активного сегмента и точное число байтов следующих кадров.
`append(segment_id, part)` проверяет ZMS-часть и записывает её кадр `ZMSP`.
Первое добавление одной операцией синхронизации фиксирует на диске идентификатор
сегмента и первый кадр. При следующих добавлениях требуется тот же идентификатор.

`Journal::open` проверяет весь заголовок и все кадры, не загружая файл целиком в
память. Метод отклоняет журнал без заголовка, журнал другой версии, а также
журнал, повреждённый из-за неполной записи или по другой причине, и оставляет
его без изменений. Файл нулевой длины инициализируется пустым заголовком.

`JournalConfig::max_journal_len` ограничивает физический размер файла с учётом
временного 32-байтового маркера сброса. При каждом добавлении, включая первое,
место под маркер резервируется заранее. Если добавление кадра превысит предел,
метод возвращает `JournalError::Full`, чтобы сборщик сначала записал открытый
сегмент. Журнал версии 1 вмещает не более 1 GiB и 1 000 000 кадров, а одна
ZMS-часть — не более 64 MiB. В конфигурации эти абсолютные пределы можно только
уменьшить.

`reset` допустим только после успешной публикации сегмента. Сначала он добавляет
и синхронизирует маркер с длиной до сброса, `SegmentId` и контрольной суммой
заголовка. Затем записывает `JournalHeader::EMPTY` и вызывает `sync_data`, пока
маркер и тела кадров ещё находятся в файле. После этой синхронизации файл
усекается до 36 байт, а `sync_data` вызывается второй раз. Если процесс
завершается после фиксации маркера, следующий `Journal::open` проверяет маркер и
заканчивает сброс. Ошибка отката или сбой после фиксации маркера переводит
открытый журнал в состояние poisoned: каждая следующая операция возвращает
ошибку, демон завершается, а следующее открытие журнала доводит сброс до конца
по зафиксированному маркеру.

## Запись

`write_segment(journal, owner, SegmentAddress)` проверяет каждую записанную часть
и читает каждое тело по проверенному диапазону каталога. Для каждого
зарегистрированного `type_id` данных функция декодирует все тела журнала и
объединяет их строки. Затем она сортирует строки по ключу реестра и по всем
остальным столбцам, получая детерминированный полный порядок, и создаёт одно
каноническое тело Parquet. Тела словарей декодируются и нормализуются максимум
в одно тело `dict.strings` и одно тело `dict.blobs`. Точные повторы словарных
записей удаляются; при конфликте значений, метаданных или размещения запись
завершается ошибкой.

Готовые тела используют Parquet 1.0, значения PLAIN, уровни RLE и Zstd уровня 6;
словарное кодирование, статистика и индексы смещений отключены. Окна сбора
добавляются без прогноза размера итоговой секции. При декодировании и
кодировании `write_segment` проверяет ширину полей каталога, объём работы,
арифметику, допускает несколько страниц Parquet и проверяет фактическое тело
по пределу версии 1 в 1 GiB.

`write_segment` записывает объединённые тела и концевой каталог во временный
файл в каталоге дня UTC. При публикации ZMS файл синхронизируется, каноническое
имя `YYYY/MM/DD/N.zms` добавляется жёсткой ссылкой, каталог дня синхронизируется,
временное имя удаляется, затем каталог синхронизируется ещё раз. Существующий
файл не перезаписывается. При восстановлении существующий ZMS принимается,
только если он проходит структурную проверку и побайтово совпадает с созданным
сегментом.

После получения блокировки владельца записи сборщик при запуске удаляет только
распознанные временные файлы публикации ZMS, оставшиеся от прежнего процесса.
Временные файлы IDX и временные файлы проверки возможности записи IDX он не
трогает: их удаляет владелец индекса.

`write_segment` не сбрасывает журнал, не выбирает `SegmentId` и не применяет
политику хранения; эти операции выполняет сборщик. `SegmentAddress` вычисляет
единственный допустимый путь по идентификатору, а код записи принимает только
этот адрес в строгом календарном дереве.

В API ошибки ввода-вывода журнала, структуры кадров и превышения пределов
отделены от ошибок проверки данных перед записью, работы с файлом назначения и
синхронизации. Описание API находится в [`src/lib.rs`](src/lib.rs), структуры
кадров на диске — в [`../kronika-format/`](../kronika-format/), путей и прав
записи — в
[`../kronika-layout/`](../kronika-layout/).
