# Класс 1: операционная система и cgroup

[English version](os.md)

Этот справочник связывает записанные показатели Linux с файлами-источниками и пределами чтения. Данные одного типа хранятся в секции сегмента. Идентификаторы типов ОС занимают `1_100_001`–`1_299_999`; точные поля определены в [реестре](../../crates/kronika-registry/src/codec). Формулы показателей интерфейса вынесены в [справочник Linux](../metrics-linux.ru.md). Cgroup — группа процессов Linux с общим учётом и ограничениями CPU, памяти и других ресурсов.

Поле `scope` в каждой строке указывает, к какой машине, группе контейнеров или контейнеру относятся данные:

| Код | Область |
| ---: | --- |
| `0` | узел (`host`) |
| `1` | pod — группа контейнеров |
| `2` | сетевое пространство имён pod (`pod_net`) |
| `3` | контейнер |
| `4` | не определено |

CPU, память, диски, точки монтирования и топология описывают машину, даже если сборщик находится в контейнере. При записанном контейнерном окружении сетевые секции используют `pod_net`. Процессы получают `container` внутри контейнера и `host` вне него. Секции cgroup собираются только в контейнере.

Корни файловых систем можно переопределить через `KRONIKA_PROC_ROOT` (по
умолчанию `/proc`) и `KRONIKA_SYS_ROOT` (по умолчанию `/sys`).

## Зарегистрированные типы

Сейчас сборщик записывает форматы `1_201_001` и `1_202_001`. Форматы `002`
остаются в реестре, поскольку они встречаются в существующих файлах WAL и ZMS.

В секции cgroup входят только группы, непосредственно названные у живых процессов `/proc/<pid>`. Сборщик не приписывает родителю данные всех потомков. В cgroup v2 используется единый путь группы; в v1 пути контроллеров CPU, памяти, ввода-вывода и потоков раздельны. Строка CPU создаётся, только если `cpu` и `cpuacct` указывают один путь. За проход допускаются 512 пар «контроллер/путь» и 512 KiB текста путей; превышение любого предела исключает все секции cgroup этого прохода. Более 1024 строк «cgroup/устройство» исключают только секцию ввода-вывода; секции CPU, памяти и потоков сохраняются. Периоды сбора cgroup и принадлежности процессов по умолчанию равны 30 секундам. При совпадении проходов используются уже прочитанные пути процессов. Каждый корректный счётчик устройства записывается независимо: отсутствие байтов не исключает число операций и наоборот.

`os_cgroup_context` хранит точные пути контроллеров для процесса сборщика из
`/proc/self/cgroup`. В cgroup v2 для CPU, памяти и ввода-вывода записывается
единый путь. В cgroup v1 пути контроллеров остаются раздельными. Поле
`cpuset_cpus` содержит число CPU из `cpuset.cpus.effective` в v2 или
`cpuset.effective_cpus` в v1. Если нужный файл отсутствует или не разбирается,
поле равно `null`. При сборе cpuset сборщик не ищет значение у предка и не
подставляет число CPU хоста.

Поля `effective_cpu_quota_usec` и `effective_cpu_period_usec` хранят точную
пару с минимальным отношением квоты к периоду на пути от настроенного корня
cgroup до конечной cgroup процесса. Квота `-1` с положительным периодом
означает, что все обязательные уровни с файлами контроллера проверены и не
задают предела. Оба поля равны `null`, если обязательный уровень отсутствует
или содержит непригодное значение. В cgroup v2 файл `cpu.max` читается от корня
монтирования до конечной cgroup. Для принадлежности ниже корня только ошибка `NotFound` в
самом корне означает неограниченный настоящий корень; все дочерние файлы
обязательны. Другие ошибки корня не игнорируются, а принадлежность самому корню
требует читаемого корневого файла. В cgroup v1 сборщик однозначно привязывает
корень контроллера CPU по конечной cgroup, а затем читает `cpu.cfs_quota_us` и
`cpu.cfs_period_us` у каждого предка только из этого корня. Для квот `Q₁`, `Q₂` и периодов `P₁`, `P₂` сравнение выполняется без деления: `Q₁ × P₂ < Q₂ × P₁`. Все четыре величины измеряются в микросекундах.

Поле `effective_memory_max` хранит минимальное конечное значение `memory.max`
в той же точной иерархии cgroup v2 по тому же правилу корня монтирования. В
cgroup v1 используется проверенный `hierarchical_memory_limit` точной конечной
cgroup, который уже учитывает семантику иерархии ядра. Это значение и
`memory.limit_in_bytes` конечной cgroup должны читаться из одного привязанного
корня контроллера. Конечный иерархический лимит не может превышать конечный
локальный лимит, а неограниченный иерархический лимит не может сочетаться с
конечным локальным. Поле равно `null` для проверенного неограниченного значения
и когда эти данные не удалось прочитать согласованно. Значение `-1` и значения
v1, не меньшие половины `i64::MAX`, являются признаками отсутствия лимита и не
выдаются за байты.

`cgroup_version` равен `0`, если сведения о принадлежности не удалось прочитать
или сопоставить с деревом cgroup, из которого собираются данные. В cgroup v1
поле `cpu_path` равно `null`, когда контроллеры `cpu` и `cpuacct` помещают
процесс в разные пути: в этом случае нет одной строки CPU cgroup, где
одновременно есть потребление и квота. Путь контроллера также равен `null`,
если в текущем сохранённом формате нет хотя бы одного счётчика или компонента,
который показывает web: неполные старые файлы не представляются нулями.
Локальные столбцы квоты CPU и лимита памяти по-прежнему показывают точные файлы
конечной cgroup и не переименовываются в эффективные значения иерархии.

Период сбора не входит в `type_id`. Планировщик сборщика задаёт его для
каждого источника; интервалы и значения по умолчанию перечислены в
[README сборщика](../../bins/kronika-collector/README.md).

CPUFreq объединяет CPU, частотой которых ядро управляет совместно; такая группа называется политикой. `1_121_001` хранит список `related_cpus`, драйвер, выбранный источник фактической частоты и аппаратные пределы в целых герцах. `1_122_001` хранит одно измерение на политику. При каждом чтении сборщик предпочитает успешно разобранный `cpuinfo_avg_freq`, затем `cpuinfo_cur_freq`; если оба недоступны, значение и источник равны `null`. `scaling_cur_freq` хранит отдельно заявленную или запрошенную рабочую частоту политики.

## Ограничения

Одна операция чтения procfs ограничена 4 MiB константой формата. Число строк в
снимке процессов не ограничено: хост с тридцатью тысячами процессов создаёт
тридцать тысяч строк. Для справочника пользователей действуют отдельные
ограничения, описанные ниже. Сообщение `segment_write_finish` в логе содержит
пиковый RSS в поле `rss_kib`.

## Единицы

Каждый столбец накопительного счётчика (`counter`) или обычного значения (`gauge`) объявляет единицу измерения. Проверка реестра отклоняет столбец без единицы. Используются следующие обозначения:

| Единица | Где используется |
| --- | --- |
| `none` | безразмерное число, например средняя нагрузка |
| `count` | объекты: процессы, потоки, дескрипторы, прерывания, пакеты |
| `bytes` | счётчики байтов |
| `kib` | значения в кибибайтах, которые ядро выводит в `/proc/meminfo` |
| `pages` | страницы памяти размером `instance_metadata.page_size_bytes` каждая |
| `sectors` | 512-байтные секторы из `/proc/diskstats` |
| `seconds`, `milliseconds`, `microseconds`, `nanoseconds` | время |
| `jiffies` | такты планировщика: `instance_metadata.clock_ticks_per_sec` в секунду |
| `hertz` | тактовая частота |
| `megabits_per_second` | согласованная скорость соединения |
| `percent`, `celsius` | объявлены и не используются в секциях ОС |

Описание полей `TypeContract` входит в программы чтения и записи при компиляции. В секциях сегмента хранятся значения без повторения единиц измерения.

Ёмкость файловой системы заполняется только для явно заданного списка локальных
типов: `ext2`, `ext3`, `ext4`, `xfs`, `btrfs`, `f2fs`, `zfs`, `tmpfs` и
`overlay`. Для сетевых, FUSE/userspace, `autofs` и неизвестных типов поля
ёмкости содержат `null`. Для всего прохода действует общий тайм-аут в одну
секунду; результаты, полученные до его истечения, сохраняются.

Поля идентификации `1_112_002` — `(major, minor, mount_point)`, поэтому две точки монтирования одной файловой
системы остаются разными. `root` — поле 4 из mountinfo. Записанные
`free_bytes = f_bavail × f_frsize`, `available_inodes = f_favail` берутся из `statvfs`. `1_123_001`
записывает по строке на каждую точную связь из sysfs: признак раздела с его
непосредственным родительским `dev` и слой dm/LVM/MD с каждым устройством из
`slaves/`. Для обычных целых устройств, неразрешённых ссылок sysfs и
происхождения bind mount связь не выводится. В контейнере `1_108_001`
сохраняет устройства с неслужебной точкой монтирования и устройства, которым
`io.stat` собственной cgroup сборщика начисляет I/O, поэтому физические слои
под смонтированным томом остаются названными, а `1_123_001` хранит только связи
на цепочках под этими устройствами. `1_112_002` никогда не записывает точки
монтирования внутри `/proc` и `/sys`: среды выполнения контейнеров маскируют
там пути пустым tmpfs.

`os_user` записывает в открытый сегмент не более одного соответствия для
каждой наблюдаемой пары `(scope, uid)`. Кандидатами становятся только реальные
и эффективные UID успешно разобранных строк `os_process`. Новый UID,
появившийся позднее в том же сегменте, добавляется через обычный WAL; после
ошибки добавления он остаётся кандидатом для следующего окна. Строка хранит
время сбора, UID, ссылка на имя в словаре и принадлежность ресурсов `scope`.

Сборщик читает только `/etc/passwd` и только один раз для каждого открытого
сегмента. Размер чтения ограничен 256 KiB, строка — 4 KiB, разобранный снимок —
4 096 записями, имя пользователя — 256 байтами. Ошибочные и слишком длинные
записи пропускаются; слишком большой файл или число записей отключает только
обогащение именами в этом сегменте. Запросов к NSS, LDAP, SSSD или веб-сервисам
нет. Поэтому отсутствующие и динамические пользователи остаются числовыми в
API и интерфейсе.

Код чтения соединяет `os_process` только с `os_user` и `dict.strings` того же
сегмента по ключу `(scope, uid)`. Человеко-читаемые селекторы `user` и
`effective_user` вычисляются сервером до сортировки и пагинации;
`user_id` и `effective_user_id` остаются точными числовыми селекторами. Обычный
текстовый поиск охватывает команду и оба найденных имени. При запросе данных
живая база пользователей хоста не читается.

Таблица процессов показывает накопительные поля как скорости между снимками. Для полного процессорного времени с запуска есть отдельное поле `cpu_time_ticks = utime + stime`: сумма пользовательских и системных тактов CPU.

## Что не собирается

| Несобираемая метрика | Интерфейс ядра или библиотеки |
| --- | --- |
| Инструкции, циклы и другие счётчики PMU | `perf_event_open` |
| Загрузка и память GPU | NVML через вспомогательный демон |
| Сетевой I/O по каждому процессу | Модуль ядра `netatop` |
| Счётчики портов Infiniband | `/sys/class/infiniband` |
| Занятость кэша последнего уровня и пропускная способность памяти | `/sys/fs/resctrl` |
| Строки по каждому потоку и `wchan` | `/proc/PID/task/*` |
| Proportional set size | `/proc/PID/smaps_rollup` |
| KSM, ZFS ARC, баллонинг памяти гипервизором | `/sys/kernel/mm/ksm`, состояние модуля ZFS |
