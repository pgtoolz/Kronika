# Сбои хранения и восстановление

[English version](storage-recovery.md) · [Сервисы](services.ru.md)

Kronika сохраняет собранные данные в трёх видах файлов:

| Файл | Содержимое | Кто записывает |
| --- | --- | --- |
| `active.wal` | Текущий дописываемый журнал: завершённые порции собранных данных, из которых ещё предстоит создать готовую запись. Это отдельный журнал, не WAL самого PostgreSQL. | Сборщик |
| `YYYY/MM/DD/<segment-id>.zms` | Готовая сжатая запись — сегмент. | Сборщик; `kronika-dump slice` может создать отдельный ZMS-файл. |
| `.idx` рядом с ZMS | Сводные значения и положения строк, вычисленные по записи для ускорения запросов. | Веб-сервер |

## После внезапной остановки сборщика

OOM kill — завершение процесса из-за нехватки памяти на машине или в контейнере.
Как и `SIGKILL`, оно может прервать запись без выполнения кода остановки.
Журнал может остаться корректным или содержать недописанную порцию данных:
это зависит от момента завершения процесса. Данные, оставшиеся в буферах сбора,
ещё не попали в журнал и не могут быть восстановлены из него.

При каждой дописи сборщик записывает порцию данных и соответствующий заголовок
отдельными операциями, затем вызывает `sync_data`. Только после успешной синхронизации
допись считается завершённой. За один цикл сбора может быть несколько дописей:
ранние порции могут сохраниться, даже если цикл не завершился. Если операция
записи вернула ошибку, работающий процесс пытается откатить допись; завершённый
процесс этого сделать не может. Синхронизация запрашивает сохранение данных у
файловой системы. Завершение процесса само по себе не очищает файловый кэш
операционной системы; при отключении питания данные из этого кэша могут быть
потеряны. Сохранность также зависит от успешной синхронизации файловой системой и накопителем.

Готовый ZMS сначала записывается во временный файл и синхронизируется. Затем
добавляется окончательное имя без замены существующего файла, и синхронизируется
содержащий его каталог. Временное имя удаляется, после чего каталог снова
синхронизируется. Только успешная публикация позволяет очистить журнал.

## Что сборщик делает при запуске

Сборщик проверяет сигнатуру и версию журнала, контрольную сумму заголовка,
состояние и идентификатор сегмента, соответствие указанной длины размеру файла,
а также каждую записанную порцию данных. Проверяются границы записей, ограничения
размера, каталог секций и контрольные суммы CRC32C. CRC32C позволяет обнаружить
изменённые байты, но не восстановить их.

| Состояние журнала | Результат запуска |
| --- | --- |
| Файл отсутствует или имеет нулевой размер | Создаётся пустой журнал. У подготовленного пустого журнала есть заголовок размером 36 байт. |
| Весь заполненный журнал корректен | Создаётся ZMS с идентификатором сегмента из заголовка, затем журнал очищается. Новый сбор начинает новый сегмент. |
| Неполный заголовок или последняя порция данных, несовпадение длины, повреждённая запись или контрольная сумма | Запуск прекращается; существующий `active.wal` остаётся без изменений. Исправное начало не публикуется отдельно, последняя порция не отбрасывается. |
| Контрольные суммы верны, но данные Parquet не читаются, тип записи неизвестен или схема несовместима | Создание сегмента завершается ошибкой; журнал остаётся на месте. Проверка контрольных сумм не заменяет разбор данных. |
| Превышен настроенный предел размера журнала или предел числа порций в формате | Журнал не открывается; ограничение не обрезает файл. |
| Проверена отметка уже начатой очистки журнала | Очистка завершается после проверки отметки, допустимого перехода заголовка и прежних порций данных. |

Автоматического исправления по правилу «оставить всё до последней целой записи»
нет. Низкоуровневый сканер умеет найти исправное начало, но сборщик требует
корректности всего заполненного журнала. Сохранённые порции сохраняют строки и
общие границы времени; поле `window_count` готового каталога считает порции
журнала, а не обязательно циклы сбора. Сбор не продолжается внутри восстановленного
таким образом сегмента.

Если ZMS по этому имени уже существует, он должен пройти проверку и побайтово
совпасть с заново сформированным файлом. Другой существующий файл не
перезаписывается. У очистки журнала есть собственная синхронизируемая отметка:
после публикации сборщик записывает её, затем пустой заголовок и обрезает файл
до 36 байт. Проверенную незавершённую очистку можно закончить при запуске;
это не исправляет произвольные повреждения заголовка или данных.

Успешная запись восстановленного сегмента отмечается событием
`segment_write_finish` с `reason=recovered` и `segment_path`. Оно появляется
до очистки журнала. После успешной очистки в stdout появляется
`wrote <path> reason=recovered`, а после подготовки сборщика — `ready`.
Ошибка открытия содержит `open active.wal; the existing file is preserved on failure`.
При ошибке записи восстановленного сегмента или очистки журналируется
`segment_close_failure`, `reason=recovered` и этап `write` или `journal-reset`.

## Чтение журнала во время сбора

Читатель фиксирует идентификатор журнала и границу завершённых записей в байтах.
Он читает только порции до этой границы; последующая допись не расширяет уже
начатое чтение. Ранее выбранные данные могут оставаться доступны, пока следующая
порция дописывается. Если журнал очищен, заменён или начат другой сегмент, старое
чтение может завершиться ошибкой изменения источника. Повторный выбор данных
из нового сегмента не восстанавливает повреждённые байты.

Новый обход каталога проверяет зафиксированную длину журнала и все порции в ней.
Неполная или повреждённая допись может исключить активный журнал с предупреждением,
при этом готовые записи остаются в списке. Это возможно и во время дописи;
само предупреждение ещё не доказывает постоянное повреждение. Проверенная отметка
очистки означает пустой активный журнал после проверки прежних порций.
**Веб-сервер никогда не обрезает, не очищает и не исправляет `active.wal`.**

## Когда проверяются готовые записи

Секция — набор строк одного записанного типа, например измерений процессов.
ZMS хранит каждую секцию сжатой, а в каталоге указывает её положение в файле,
число строк и контрольную сумму. Проверки выполняются поэтапно:

| Операция | Что проверяется |
| --- | --- |
| Получение каталога веб-сервером | Сигнатуры `ZMS1` в начале и конце, длины завершающей части и каталога, версия формата, контрольная сумма каталога, порядок секций и их непересекающиеся границы внутри файла. Тела секций не читаются и не распаковываются. |
| Получение списка с проверкой данных, в том числе обычный `kronika-dump` | Та же структура, затем контрольная сумма каждой секции выбранных готовых сегментов. Тела файлов вне выбранного интервала времени так не проверяются. |
| Чтение строк запрошенной секции | CRC32C её записанных байтов, метаданные Parquet и ограничения чтения, число строк и ожидаемая схема. Распаковка и разбор строк могут завершиться ошибкой по мере чтения. Нужные словари читаются отдельно; остальные секции целиком не разбираются. |

Например, обрезанный каталог может сразу исключить весь файл. Изменённый байт
в секции может оставить файл видимым в каталоге, но вызвать ошибку при чтении
этой секции. Даже при совпавшей контрольной сумме некорректная страница Parquet
или поле неверного типа могут помешать разбору. Открытие каталога или одного
графика не означает проверки всех строк записи.
[Справочник формата](../crates/kronika-format/README.ru.md) определяет точное
расположение данных, ограничения и область расчёта контрольных сумм.

## Отсутствующие и повреждённые индексы

Для готового локального ZMS веб-сервер заново строит отсутствующий индекс,
открытый индекс с неверным форматом или контрольной суммой либо индекс без
обязательных для запроса блоков. Это относится и к устаревшим заголовкам:
текущий формат — `KRNIDX1`. Для построения читается ZMS, временный индекс
записывается и синхронизируется, затем атомарно заменяет `.idx` после повторной
проверки исходного файла. Если индекс невозможно открыть из-за прав доступа
или ошибки файловой системы, запрос может завершиться ошибкой ещё до построения.
Оно также может не удаться, если ZMS не читается или индекс нельзя записать.

Исправный IDX может отвечать на запросы сводных значений, даже если тело ZMS
повреждено: при этом исходные данные повторно не читаются. Индекс не
восстанавливает исходные строки и не делает их доступными для чтения. HTML-отчёт
использует встроенные ZMS и IDX в памяти: проверяет переданный индекс и не
строит заново отсутствующий или повреждённый индекс в браузере.

## Что возвращает веб-запрос

| Запрос или этап | Результат при ошибке чтения хранилища |
| --- | --- |
| Обход для каталога | Неверные или недоступные файлы могут исключаться с предупреждениями, а другие записи остаются доступны. Ошибка доступа к корню или обхода каталога может прервать запрос. Браузер отфильтровывает предупреждения каталога; исключённый файл не обязательно вызывает видимую панель ошибки. |
| Запрошенные данные до отправки заголовков | Ошибка чтения возвращает HTTP `500` с `{"error":"unreadable"}`, в том числе пока сервер ещё удерживает первые байты результата перед отправкой. |
| Запрошенного сегмента или секции нет | HTTP `404` с `{"error":"no_such_segment"}` или `{"error":"no_such_section"}`. |
| Поток данных после отправки заголовков и начальных байтов | Передача тела ответа обрывается. Уже отправленный HTTP-статус изменить нельзя; завершающая строка NDJSON с ошибкой не добавляется. Полученные строки не образуют полный успешный результат. |
| Экспорт HTML | Предупреждение о неверном ZMS или активном журнале останавливает экспорт с HTTP `500`, `export_failed`, в том числе для файла вне запрошенного интервала. |
| Название экземпляра | Ошибка чтения записывается в лог, а запрос получает HTTP `200` с `database: null`. |

Если выбранный файл изменился во время чтения и ошибка допускает новый выбор
данных, веб-сервер повторяет запрос один раз до отправки заголовков. Повторная
ошибка завершает запрос; ошибки контрольной суммы и разбора так не повторяются.
После начала передачи сервер обрывает ответ, не смешивая данные разных версий
файла. Браузер отдельно повторяет один раз неудачную передачу по сети, но не
повторяет запрос после ошибочного HTTP-статуса.

Ошибка запроса не останавливает веб-сервер. Запросы к другим доступным данным
могут завершаться успешно. При неудачной первоначальной загрузке часа браузер
показывает ошибку. У неудачной загрузки таблицы есть отдельное состояние ошибки,
отличное от успешного пустого результата; ранее загруженные строки этой же
таблицы могут остаться видимыми. При сбое обновления сохраняется рабочее
представление. Некоторые дополнительные запросы, например сведения о группах
процессов с общими ограничениями ресурсов (cgroup), только записывают ошибку в
консоль браузера и сохраняют основные строки. Предупреждения каталога сами по
себе не открывают панель ошибки.

## Как посмотреть ошибку

Для служб из [руководства по сервисам](services.ru.md) прочитайте оба журнала:

```sh
sudo journalctl -u kronika-collector -u kronika-web --since '10 minutes ago'
sudo kronika-dump /var/lib/kronika
sudo kronika-dump /var/lib/kronika --json
sudo kronika-dump /var/lib/kronika --section 1100001 --limit 10
```

Замените `/var/lib/kronika` своим каталогом данных. Ошибки сборщика указывают
операцию; события сегмента содержат `segment_path`. Веб-сервер записывает
ошибки чтения API с исходным сообщением, но предупреждения обхода содержат
только код. Предупреждение каталога указывает сегмент или активный журнал;
полного пути может не быть. Идентификатор готового сегмента соответствует
`YYYY/MM/DD/<segment-id>.zms` в каталоге данных.

`kronika-dump` проверяет структуру и контрольные суммы секций, затем выводит
допущенные к чтению сегменты. Предупреждения идут в stderr, а с `--json` —
отдельными записями в stdout. **Предупреждения возможны и при коде завершения 0:**
смотрите их вместе с результатом. `--section` дополнительно разбирает выбранный
тип и нужные словари; пример выводит до 10 строк на сегмент. Ошибка разбора,
возвращённая командой, даёт ненулевой код завершения. Обе команды просмотра
оставляют входные файлы без изменений. Фраза `set aside` в диагностике означает
исключение из этого обхода, а не перемещение файла на диске.

После OOM kill обычный запуск автоматически обрабатывает корректный журнал.
Если повреждённые байты мешают запуску, сохраните файл для изучения: повторный
запуск не превращает его в исправленный журнал. Команды для восстановления
потерянных байтов WAL/ZMS нет. Повторное построение относится только к
производным файлам IDX. [Справочник dump](../bins/kronika-dump/README.ru.md)
описывает просмотр и извлечение интервала; извлечение не исправляет исходный файл.
